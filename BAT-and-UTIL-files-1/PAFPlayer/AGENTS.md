# PAFPlayer project instructions

These instructions apply to the PAFPlayer project. They include Claire's shared
C:\BAT, Python utility, backup, and Recycle Bin rules. Keep them here even if
there is no parent AGENTS.md in the workspace checkout.

## Files and change disclosure

Always tell the user whenever any file under C:\BAT is created, modified,
deleted, renamed, replaced, copied as a release artifact, or generated by a
test (including bytecode). In the final response, list every affected C:\BAT
path and its status. A deployment or synchronization into C:\BAT counts even
when the tested workspace file is identical. Do not claim C:\BAT changed when
only the C:\codex workspace changed.

Never permanently delete a file or directory. Send any deleted item to the
Windows Recycle Bin. If recycling is unavailable or fails, stop; never fall
back to permanent deletion. Prefer moving old material into an archival
subfolder when it remains useful. Before any recursive move, verify that both
resolved paths remain within the intended project or explicit destination.

Whenever a created, copied, moved, recycled, restored, or backup filename
would collide, preserve both items with ` (1)`, ` (2)`, and so on immediately
before the final extension. Never overwrite an existing release artifact.

Before replacing file contents or embedded metadata in place, create and
verify a sibling backup named
`<filename>.bak.YYYYMMDDHHMM.replaced-by-chatgpt.bak`. For a collision,
insert ` (1)`, ` (2)`, and so on before the final `.bak`. Verify the backup
matches the original before editing, regardless of file size. To keep working
roots clear, move a verified backup to the designated archive after the change:
PAFPlayer.py backups to `releases/`, AGENTS.md, TODO, changelog, and test-runner
backups to `backups/`, documentation backups to `docs/`, and integration
backups to their own archive. Preserve the backup; never recycle it as part of
routine cleanup.

## Shared Python utilities

Put every reusable ClaireCJS Python utility library in `C:\clairecjs_utils`.
That path is currently a junction to
`T:\ProgramData.Demona.ssd-spillover\anaconda3\Lib\site-packages\clairecjs_utils`.
`C:\BAT\clairecjs_utils` is a separate mirrored directory; keep the
corresponding library file synchronized there and in the `clairecjs_bat`
repository copy. For any Python color-cycling progress bar, use
`clairecjs_utils.claire_progressbar`. Rainbow cycling is the default; pass
`rainbow=False` only if the task or user explicitly requires a non-rainbow bar.

## Version, documentation, and verification

Every code, behavior, feature, configuration, or layout change increments the
PAFPlayer version. Update the active `PAFPlayer.py`, add a uniquely named
`releases/PAFPlayer_v{version}_{description}.py` copy and versioned release
notes, then update `docs/PAFPlayer_changelog.md` in newest-first order.
Update the appropriate full document under `docs/` in the same change.
`PAFPlayer.md` at the root stays a short description and link to full docs.
When completing a TODO, document the feature before checking off or removing
the entry in `docs/PAFPlayer_TODO.md`.

Put test reports and generated test-result files in `tests/reports/`; use
`tests/runs/` only for isolated staging fixtures. Run focused and relevant
existing tests, syntax checks, and single-file bundle/source parity checks.
Do not declare a release complete until its source, documentation, and release
copy agree.

## Single-file distribution goal

Keep the runnable Windows player self-contained in `PAFPlayer.py` as far as
possible. Store editable feature-module sources in `src/`, tests in `tests/`,
build and maintenance tools in `tools/`, full documentation in `docs/`, and
prior releases in `releases/`. The project root should contain one runnable
Python file. `AGENTS.md` is the instruction-file exception to the rule that
`PAFPlayer.md` is its only root documentation file. Preserve active data
sidecars such as `PAFPlayer.dcc`, playlists, and the Last.fm setup marker until
all references are safely migrated; directory tidiness must not change active
settings or playback.

For self-installation, if `C:\BAT` exists, choose `C:\BAT\PAFPlayer`.
If occupied, choose `C:\BAT\PAFPlayer_v{version}`. If occupied again, choose
`C:\BAT\PAFPlayer_v{version}_YYYYMMDDHHMMSS`, followed by the collision suffix
rule if needed. If `C:\BAT` does not exist, use `%LOCALAPPDATA%\PAFPlayer`
with the same version and timestamp fallback. Never overwrite an existing
installation or move a running script: stage and verify a copy, launch the
installed copy, and preserve user data. V606 implements this staged core
single-file installation and the read-only `--readiness-check`. Do not infer
that native tools, Python packages, or optional Windows integrations have
been installed just because the source copy succeeded. A failed readiness
check leaves the copied install in place without starting playback.

Every release must audit and tidy the roots of `PAFPlayer/`, `lockscreen/`,
and `screensaver/`. Keep only active implementation and required runtime files
at those roots. Move historical builds, test output, probes, diagnostics,
bytecode, old scripts, and backups into their designated subfolders without
permanent deletion. Keep lock-screen project inputs together so its build
still works, and keep its `dist/` assets available to the direct installer.
The screensaver's active `.scr` and configuration stay where the player finds
them; its source and builder belong in subfolders.
